# 系统演进工作流

严格遵循 `docs/02-architecture.md` 的演进边界：**记录失败 → 限定范围改动 → 固定基准日评上比较 → 回归检查 → Critic 审查 → 人工批准 → 版本注册表登记 → 可回滚。** Orchestrator 仍是唯一枢纽，所有验收阈值继续引用 `policies/policy.json`，不得为促成演进通过而修改标准。

## 1. 记录失败并取得演进授权

1. 读取失败事件、问题项台账、相关版本和证据哈希，明确需要解决的可复现问题。
2. 由 Orchestrator 登记演进范围、授权路径和预期产物；Evolution 负责人只做分派与整合，不写日评正文。
3. 没有具体失败证据或演进授权时不得开始改动。

## 2. 冻结固定基线日评

1. 从版本注册表选择一个已登记、证据完整且与本次失败相关的基线版本，不得使用可变的“最新文件”代替固定版本。
2. 登记基线版本号及其不可变产物的绝对路径和 SHA-256，至少包括已发布日评、确定性指标 JSON、数据快照与 manifest、模板、策略文件和计算脚本版本。
3. 保存基线的人工批准记录引用，但批准记录与版本记录保持分离；不得复制旧批准给新候选。
4. 将基线比较所需输入、历史留出案例、信息截止时点和运行环境说明一并固定，形成基线清单。
5. 冻结后不得覆盖基线文件或按候选结果调整留出案例；哈希不符时阻断比较。

## 3. 提出限定范围的改动

每份演进任务包必须写明：

- 对应失败编号和拟验证的改动目的；
- 允许修改的文件或能力边界、明确不改的部分和输入输出绝对路径；
- 固定基线版本、比较范围、完成定义和所需证据；
- 回滚方式和可能受影响的下游产物。

改动必须最小且可定位，不得同时夹带无关重构、数据源替换、模板改名或阈值调整。不得改变任务授权、信息截止规则或人工批准边界。需要扩大范围时，返回 Orchestrator 重新授权，而不是自行扩展。

## 4. 在基线上比较并执行回归检查

1. 对基线版本和候选版本使用同一批冻结输入、同一信息截止时点及一致的执行条件。
2. 分别保存确定性计算结果、候选日评、检查关卡输出和证据哈希；不得覆盖基线产物。
3. 比较目标失败是否消除，并逐项比较数值一致性、模块完整性、时点合规、格式与措辞结果。
4. 在固定历史留出案例上执行 `check_consistency`，记录改善、无变化和劣化项，不得只展示对候选有利的案例。
5. 任一历史留出案例出现策略所定义的劣化，或必要检查未执行，均不得宣称回归通过。
6. 将完整比较报告、失败复现证据和回归结果交给 Orchestrator；由 Orchestrator 路由给 Critic 进行新上下文独立审查。

## 5. 人工批准与版本注册

1. Critic 审查通过且不存在未解决问题项后，Evolution 负责人整理候选版本、基线比较、回归报告、审查证据和回滚说明。
2. Orchestrator 将候选版本登记为待人工批准并停止自动推进；不得将回归通过或 Critic 通过视为发布授权。
3. 等待明确人工 `approve`。批准记录必须具名、绑定候选的准确版本和哈希、包含有效期，并与版本记录分开保存。
4. 人工批准关卡通过后，方可在版本注册表登记新版本的产物路径、SHA-256、父版本、基线比较、回归结果、批准记录引用和回滚目标。
5. 未获批准、批准过期或版本哈希变化时不得登记为可用版本，必须重新审查和批准。

## 6. 回滚

1. 发现新版本劣化或需要撤销时，记录原因、影响范围和证据，由 Orchestrator 选择版本注册表中证据完整的先前版本。
2. 核对回滚目标的产物路径和 SHA-256，确认其独立批准记录有效且绑定该版本；不得仅修改一个“当前版本”指针而缺少轨迹。
3. 保留失败版本及其历史记录，不删除、不改写；将回滚事件、操作者、时间和目标版本写入轨迹与版本注册表。
4. 回滚后在固定基线和必要留出案例上重新执行检查，并由 Critic 审查；涉及再次发布时仍须通过对应人工批准门。
5. 若回滚目标证据缺失、哈希不一致或授权无效，则阻断，不得回退到未登记或不可复现的版本。
