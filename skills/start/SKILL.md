# 日评生成工作流

严格遵循 `docs/02-architecture.md`。Orchestrator 是唯一枢纽；不得让 Generator 与 Critic 直接交接。每个交易日使用独立 `task_id`，所有阈值、修订轮次和执行预算只读取 `policies/policy.json`，信息时点规则只读取 `policies/pit_rules.json`。

## 智能体绑定

- ReportWriter 使用现有 `agents/generator-lead.md` 角色卡，并同时加载 `prompts/report_writer_system.md` 与本 Skill；不得另建 SDK 调用。
- 指标岗由 `agents/metrics-agent.md` 驱动，通过 Bash 执行 `scripts/calculator.py`，LLM 不得自行算数。
- Verifier 由 `agents/critic-lead.md` 及四个 Critic 专项角色卡驱动；各专项通过 Bash 调用 `runtime/dailyflow/gates.py` 获取确定性 JSON 判定。
- 每个交易日使用 `output/<task_id>/` 作为运行目录，每轮报告写入 `rounds/round-NNN/generator/` 与 `rounds/round-NNN/critic/`，路由决定写入该轮的 `decision.json`。
- 运行结束后将状态、轨迹、问题项、快照、各轮报告和结果归档到 `evidence/<task_id>/`，不得仅保留被 Git 忽略的 output 证据。

## 1. 建立或恢复任务

1. 读取任务授权书，确认报告交易日、信息截止时点、时间区间和输出范围。
2. 每个分派必须登记输入绝对路径、输出绝对路径、时间区间与完成定义。
3. 新任务从 S0 开始；恢复任务先读取并校验 `state.json`、产物路径和 SHA-256，从最近的已核验检查点继续。
4. 若已处于 `drafted`，跳过采集和计算，直接核验已登记候选；不得重新生成一个不可比的新产物替代它。
5. 汇合前核验全部必需报告、身份和证据；缺失或不一致时阻断，不得静默补做。

## 2. 完成 S0 与 S1

1. 由 Generator 负责人分派数据岗，生成数据快照报告、快照 manifest、缺失登记和 SHA-256。
2. 再分派口径岗，依据快照和 `policies/pit_rules.json` 逐字段检查 `available_at`。
3. 取得自包含时点报告、可用字段清单、被排除字段清单及逐项理由。不得仅凭数据所属日期放行，也不得使用 `bfill`。

## 3. 在 S2 调用确定性计算脚本

只有同时满足以下条件，指标岗才可调用 `scripts/calculator.py`：

- S0 快照和 S1 时点报告身份、路径与哈希已通过核验；
- 所需可用字段和基期数据已经登记；
- 脚本输入、输出绝对路径和计算范围已在分派中明确；
- 前置检查失败时没有通过手工补数绕过。

按分派确定的脚本入口和参数执行确定性脚本，不得由 Agent 心算、估算、补全或修改结果。脚本缺失、执行失败、输出缺失或 schema 不符时登记阻断，不得用模型生成数字替代。

### 读取指标结果 JSON

1. 从分派预先登记的输出绝对路径读取 JSON，不把终端摘要或自然语言说明当作数值来源。
2. 解析 JSON，核对 `task_id`、输入哈希、数据日期、基期、指标标识、数值、单位和脚本执行证据。
3. 校验输出文件 SHA-256并登记到状态与证据清单。
4. 后续生成和核验均按指标标识读取同一 JSON 中的值，保留原始数值文本、精度和单位。
5. 若 JSON 缺少必需指标或字段，返回失败，不得计算补齐。

## 4. 生成候选并交给 Critic

1. Generator 负责人取得自包含的数据快照报告、时点报告和指标报告，汇合前核验三份报告、身份与证据。
2. 按 `references/template.md` 和 `prompts/report_writer_system.md` 整合候选日评，保持票据供给、缺口分析、票据利率、资金面的固定顺序。
3. 执行一致性自测，登记候选版本、产物路径与 SHA-256。
4. 将候选、三份专项报告、自测结果、指标 JSON 和快照清单一并交给 Orchestrator。
5. **只有 Orchestrator 执行必要检查关卡并决定继续后，才把候选核验输入路由给 Critic。** Generator 不得直接联系 Critic。
6. Critic 每轮以新上下文分派四个审查专项，合并覆盖检查和问题项后，仅把结果交给 Orchestrator。

## 5. 修复任务包与回退路径

Critic 未通过时，严格执行：

**Critic 合并问题项 → Orchestrator 修复任务包 → Generator 负责人 → 候选自测与登记 → Orchestrator 检查关卡 → Critic 新上下文复核。**

- 修复任务包必须包含全部未解决问题项、每项指向的受影响产物、修复所需证据、输入输出绝对路径、时间区间和完成定义。
- Orchestrator 必须作出继续或结束决定；达到 `policies/policy.json` 的修订上限或执行预算时按策略停止，耗尽不等于验收通过。
- 遗漏的问题项保持未解决，只有 Critic 复核修复后的输出才能关闭。
- 候选内容变化后登记新哈希，并按策略重新累计同一候选的连续审查通过状态。

## 6. 验收与人工批准门

只有全部必要检查通过、完整审查覆盖所有专项且无未解决问题项，并满足同一候选连续审查通过要求，才可进入人工批准等待。

等待人工批准时：

1. Orchestrator 将已核验候选和具体版本登记为待批准，保存全部产物哈希和审查证据。
2. 停止自动执行，将待处理角色登记为人工批准人；不得继续修改候选、轮询伪造批准或自动发布。
3. 向用户提供版本、产物位置和审查结论，明确等待人工 `approve`。
4. 收到批准后，核验批准记录具名、绑定同一版本、处于有效期，并与版本记录分开保存。
5. 只有批准关卡和发布关卡均由控制器判定通过，才能推进 `approved` 和 `published`。数值验收通过不等于发布授权；用户停止或未明确批准时继续等待或按授权终止，不得发布。

最终输出必须保留“输出为研究参考，不是报价指令”的边界。
